# fp2mp-core

Мультиагентная система для ответов на открытые вопросы. Принимает произвольный вопрос, декомпозирует его на подзапросы, параллельно запускает специализированных агентов, накапливает знания в общей вики и синтезирует итоговый структурированный ответ. Для города, у которого есть заранее построенная локальная модель (`data/model`: кварталы, ёмкости сервисов, население, матрица доступности), система привлекает **BlocksNetAgent** — он считает надёжные городские индикаторы и генерирует измеренные гипотезы развития (что и где строить).

## Архитектура

```
START → init → redi_decompose → init_blackboard → orchestrator
                                                │
        ┌────────────────────────────────────────┤
        │           [параллельный Send]          │
        ├──► web_search_agent ───────────────────┤
        ├──► normative_agent  ───────────────────┤
        ├──► code_spatial_agent ─────────────────┤ → wiki_curator
        ├──► blocksnet_agent ────────────────────┤
        └──► mediator ───────────────────────────┘

wiki_curator ──continue──► orchestrator   (цикл)
             ──critic────► critic
             ──finish_ready─► final_synthesis → END

critic ──continue──► orchestrator
       ──finish────► final_synthesis → END
```

### Агенты

| Агент | Роль |
|---|---|
| **OrchestratorAgent** | Читает очередь задач, выбирает оптимального агента для каждого подзапроса через LLM-рассуждение над карточками способностей, обнаруживает провальные попытки и переназначает их другому агенту |
| **WebSearchAgent** | ReAct-агент — веб-поиск и загрузка страниц; обрабатывает фактические, эмпирические и описательные подзапросы |
| **NormativeAgent** | ReAct-агент — локальная нормативная векторная БД + целевой веб-поиск; обрабатывает законы, стандарты, строительные нормы |
| **CodeSpatialAgent** | ReAct-агент — пишет и выполняет Python-код; работает с тем, чего **нет в локальной модели**: свежие данные OpenStreetMap через osmnx, геокодирование, подсчёты/измерения, дополнительные вычисления. Дополняет BlocksNetAgent, а не дублирует его |
| **BlocksNetAgent** | Tool-calling агент урбан-аналитики для города, уже заданного локальной моделью (`data/model`). Считает надёжные индикаторы через BlocksNet (обеспеченность сервисами, доступность/связность, плотность/разнообразие/центральность, морфология FSI/GSI/MXI/OSR) и генерирует измеренные **гипотезы развития**: оптимизация землепользования и набора сервисов (TPE) + независимая сценарная проверка эффекта. Работает только в пределах модели |
| **MediatorAgent** | Кросс-источниковый синтез — объединяет находки нескольких агентов, выявляет противоречия |
| **WikiCuratorAgent** | Узел fan-in — строит и ведёт общую вики, запускает ReDI Fusion, повышает факты с высокой уверенностью, обнаруживает стагнацию |
| **CriticAgent** | Оценщик — принимает решение STOP / CONTINUE, инжектирует новые задачи при обнаружении пробелов; проводит **триаж межагентных follow-ups** (валидация нужности → capability-aware выбор адресата → переформулировка вопроса под специфику агента) |

### Ключевые подсистемы

**ReDI** (Retrieval-oriented Decomposition Index) — декомпозирует вопрос на 3–5 независимых подзапросов, назначает `intent_aspect` и подсказку модальности (`web | normative | code | any`), обогащает каждый подзапрос вариантами формулировок и ключевыми словами. После декомпозиции добавляются гарантирующие подзапросы:
- `sq_code_support` — гарантированный количественный/пространственный проход (для произвольных мест без локальной модели — через CodeSpatial/OSM). Инжектируется, если декомпозер сам не выдал `code`-подзапрос.
- `sq_model_support` — гарантированный проход **по локальной модели** через BlocksNet. Инжектируется всегда, когда локация модели совпадает с вопросом (см. сопоставление локации ниже), независимо от формулировок декомпозера. Текст подзапроса — метрики модели + гипотеза развития, без OSM-токенов, поэтому пред-назначается BlocksNet.

**BlackBoard** — общее состояние LangGraph (`TypedDict`). Три уровня:
- `raw_data` — append-only журнал всех выходных данных агентов
- `wiki` — структурированные страницы знаний (upsert по page_id)
- `output` — подтверждённые факты (upsert по fact_id, побеждает более высокая уверенность)

**Маршрутизация по способностям** — оркестратор выбирает агентов через LLM-рассуждение над структурированными карточками способностей, определёнными в `capabilities.py`. Подсказка модальности из ReDI передаётся как контекст, а не как обязательное ограничение. Провальные задачи (уверенность < 0.4 или агент упёрся в лимит итераций) автоматически переназначаются другому агенту.

Разделение BlocksNet ↔ CodeSpatial (когда есть локальная модель города):
- Жёсткое предпочтение BlocksNet — только для гарантированного `sq_model_support` и для подзапросов, которые **сами по себе** девелоперские (что/где строить, оптимизация набора сервисов). Это профиль BlocksNet.
- Остальные пространственные подзапросы — это **подсказка**, а решает LLM-роутер: метрики/развитие по модели → BlocksNet; свежие OSM/веб-данные, геокодирование, дополнительные вычисления и объекты вне модели → CodeSpatial. CodeSpatial дополняет BlocksNet, а не повторяет его метрики.
- BlocksNet не ограничен одним проходом: может запускаться повторно для девелоперской задачи, ретрая проваленной или реально новой нужды.

**Сопоставление локации модели** (`text.py`) — локация локальной модели берётся из `data/model/boundaries.geojson`. Сопоставление с текстом вопроса устойчиво к кириллице/латинице и транслитерации (например, «Гатчина» ↔ `Gatchina`): обе стороны нормализуются в латиницу и сравниваются по токенам с fuzzy-порогом. Это и включает гарантированный проход BlocksNet, и подсказывает роутеру предпочесть локальную модель.

**Межагентные follow-ups (триаж)** — агенты в финальном блоке могут выносить уточняющие вопросы к другим агентам (`FOLLOW_UPS:` с адресатом). CriticAgent проводит LLM-триаж этих вопросов: проверяет, реально ли вопрос нужен и выполним; capability-aware выбирает адресата (предложенный префикс — лишь подсказка, LLM-роутинг сохраняется); и **переформулирует вопрос точно под специфику адресата** (например, не передаёт веб-агенту внутренние имена инструментов; для BlocksNet — в терминах модели: block_id, обеспеченность, сценарный пересчёт). Триаж-задаче выдаётся собственный `sub_query_id` (`…#fu`), поэтому она не блокируется анти-дубликатной логикой — это позволяет вернуть проверку обратно в BlocksNet и замкнуть петлю «гипотеза → тест».

**BlocksNet и локальная модель города** — для города, заданного в `data/model` (кварталы, ёмкости сервисов, население, предвычисленная матрица доступности), BlocksNetAgent работает через семейства инструментов в `tools/blocksnet/` (`data`, `network`, `provision`, `services`, `indicators`, `optimize`, `viz`) и реестр карточек-воркфлоу в `data/blocksnet_kb/`. Ключевой генеративный инструмент — оптимизация землепользования/сервисов:
- `suggest_target_blocks` → подбор кварталов-кандидатов;
- `propose_zone_development` (area-based **TPE**) → измеренное предложение «что и сколько строить» при заданном новом землепользовании;
- `compute_scenario_provision` → **независимая внутримодельная проверка** предложенного (или ручного) сценария: пересчитывает обеспеченность и возвращает before→after по `block_id`.

Так замыкается цикл «гипотеза развития → тест». Для генеративных вопросов («мастер-план», «что/где строить») development-директива ожидает именно измеренный вывод (оптимизатор + сценарная проверка), а не качественные рекомендации; выбор метрик и зон остаётся за агентом (без жёсткого пайплайна).

**Финальный синтез** (`nodes/synthesis.py`) — собирает подтверждённые факты и вики в итоговый ответ. Работает в режиме **fail-open**: всегда коммитит конкретный ответ (выбор / место / число / рекомендацию), никогда не отказывается и не подменяет вывод формулировками «нужно проанализировать» / «требуются данные». Приоритет отдаётся **измеренным индикаторам локальной модели** (дайджест точных чисел и `block_id` из наблюдений инструментов BlocksNet/CodeSpatial, включая артефакты оптимизатора и сценарного пересчёта) над веб-оценками. Ответ оформлен как экспертное memo из 7 секций (`Answer`; `How I'm reading the question`; `What it hinges on`; `Options I weighed`; `The case for it`; `What's still uncertain`; `Where this reasoning could be wrong`) и генерируется трёхпроходной цепочкой LLM: draft → critique → refine. Универсальные промпты (декомпозер/критик/синтез) домен-нейтральны и работают для вопроса из любой области.

## Установка

Требуется **Python 3.10+**.

```bash
# 1. Создать и активировать виртуальное окружение
python -m venv .venv
.venv\Scripts\activate        # Windows
# source .venv/bin/activate   # Linux / macOS

# 2. Установить пакет со всеми зависимостями
pip install -e ".[dev]"

# Опционально: тяжёлые пространственные и ML-зависимости
pip install -e ".[dev,spatial-extended]"

# 3. Настроить переменные окружения
copy .env.example .env        # Windows
# cp .env.example .env        # Linux / macOS
# Заполнить API-ключи в .env
```

## Конфигурация

Все настройки читаются из `.env` (полный справочник — [`.env.example`](.env.example)).

| Переменная | По умолчанию | Описание |
|---|---|---|
| `FP2MP_CHAT_URL` | `https://routerai.ru/api/v1` | OpenAI-compatible Chat Completions base URL |
| `FP2MP_API_KEY` | — | API-ключ для OpenAI-compatible backend |
| `MODEL_DATA_DIR` | `data/model` | Каталог локальной модели города (кварталы, матрица доступности, `boundaries.geojson`) — питает BlocksNetAgent |
| `MODEL_BOUNDARY_FILE` | `boundaries.geojson` | Файл границ в `MODEL_DATA_DIR`; из него берётся локация модели для сопоставления с вопросом |
| `MODEL_OUTPUT_DIR` | `data/model/output` | Куда сохраняются артефакты прогона (CSV метрик, картограммы, решения оптимизатора) |

Минимальная конфигурация:
```
FP2MP_CHAT_URL=https://routerai.ru/api/v1
FP2MP_API_KEY=sk-...
```

Модель задаётся через `.env`. Она передаётся в `run(..., model="...")`, чтобы один и тот же backend можно было использовать в `fp2mp-baselines` и `fp2mp-eval` с разными моделями и числом итераций.

## Запуск

```python
from fp2mp_core.graph import run

result = run(
    input="Какие улицы Петроградского района Санкт-Петербурга можно сделать пешеходными?",
    model="gpt-4o-mini",
)
print(result["output"])
```

С явной моделью и ограничением итераций:

```python
from fp2mp_core.graph import run

result = run(
    input="Где построить новую станцию метро в Екатеринбурге?",
    model="gpt-4o-mini",
    max_iterations=2,
)

assert {"input", "output", "log"} <= set(result.keys())
print(result["output"])
print(result["usage"])  # авторитетный итог по токенам за прогон
```

Если вопрос касается города из локальной модели (`data/model`), подключается BlocksNetAgent — он гарантированно делает проход по модели, а для генеративных вопросов формирует измеренную гипотезу развития (TPE-оптимизатор + сценарная проверка). Например:

```python
from fp2mp_core.graph import run

result = run(input="Создай мастер-план города Гатчина", model="gpt-4o-mini")
print(result["output"])  # ответ опирается на block_id, обеспеченность и предложение оптимизатора
```

`run()` возвращает `BaseState`:

| Поле | Тип | Описание |
|---|---|---|
| `input` | `str` | Исходный вопрос |
| `output` | `str` | Финальный синтезированный ответ |
| `log` | `list[BaseMessage]` | Сообщения трассировки в формате LangChain messages; каждое `AIMessage` несёт **per-message** оценку токенов (`usage_metadata`, tiktoken) |
| `usage` | `dict` | **Авторитетный** итог по токенам за прогон: `{input_tokens, output_tokens, total_tokens, source}`, где `source` = `"real"` (реальные данные бэкенда) либо `"estimate"` (tiktoken-оценка). Считается отдельно от лога, чтобы суммирование per-message оценок не задваивало этот итог |

Низкоуровневый запуск LangGraph всё ещё доступен, если нужен полный внутренний `BlackBoard`:

```python
from fp2mp_core.graph import build_graph
from fp2mp_core.state import create_initial_state

graph = build_graph()
question = "Какие улицы Петроградского района Санкт-Петербурга можно сделать пешеходными?"
state = create_initial_state(question, max_iterations=8)
result = graph.invoke(state)
```

## Бенчмарк и оценка

Сравнение с бейзлайнами и оценка качества — в ноутбуке [`examples/benchmark_fp2mp.ipynb`](examples/benchmark_fp2mp.ipynb).

- **Набор задач** — 60 ill-defined задач городского планирования (загружаются из репозитория `vasilstar97/fp2mp`).
- **Solver** — `run(..., model="gpt-4o-mini", max_iterations=3)` для бейзлайна `fp2mp`.
- **Судья** — внешний пакет `fp2mp-eval` (`FP2MPEval`, `model="openai/gpt-4.1"`, `temperature=0.5`, `n_judges=5`); рубрика из 8 измерений (см. [`reference_eval.md`](reference_eval.md)).
- **Кэш** — решения в `data/benchmark/solutions.json`, оценки в `data/benchmark/evaluations_fp2mp.json`; авто-инвалидизация по SHA256-сигнатуре `synthesis.py` (изменение синтеза помечает кэш устаревшим и перегенерирует).
- Платные прогоны (`run()` и судья) запускает пользователь вручную.
