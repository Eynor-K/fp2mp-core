## 1. Постановка задачи и центральный принцип

FP2MP решает задачи, у которых **нет единственно верного ответа**, нет фиксированного
процедурного пайплайна и нет заданной целевой функции (пример из статьи — генерация
мастер-плана города). Такие задачи требуют интеграции разнородных источников: эмпирических
данных из веба, нормативных документов, пространственно-количественных вычислений и общей
экспертизы.

Ключевой принцип: **решение как итеративное снижение неопределённости** над общим
состоянием, а не как одноразовая генерация артефакта. Архитектурно это выражено замкнутым
циклом `декомпозиция → исполнение → курирование → критика` поверх общей трёхуровневой
памяти. Свойства, отличающие LLM-MAS (координация, рассуждение, tool-use, итеративное
уточнение, агрегация, разделяемая память), не выделены в отдельные модули — они возникают
из единой графовой структуры LangGraph.

Второй сквозной принцип — **fail-open**: система всегда обязана выдать конкретный ответ
(выбор / место / число / рекомендацию) и никогда не отказывается формулировками вида
«нужно проанализировать» / «требуются данные». Отказ от ответа считается провалом, а не
допустимым исходом.

## 2. Топология графа (LangGraph)

Система собирается в `graph.py::build_graph()` как `StateGraph(BlackBoard)`.

```
START → init → redi_decompose → init_blackboard → orchestrator
                                                    │
        ┌────[Send]──► web_search_agent  ───────────┤
        ├────[Send]──► normative_agent   ───────────┤   → wiki_curator
        ├────[Send]──► code_spatial_agent ──────────┤
        └────[Send]──► mediator ─────────────────────┘

  wiki_curator ──continue──► orchestrator     (цикл)
               ──critic────► critic
               ──finish_ready─► final_synthesis → END

  critic ──continue──► orchestrator
         ──finish────► final_synthesis → END
```

**Стартовая линейная последовательность.**
- `init` (`nodes/blackboard.py::init_node`) — выставляет все дефолты состояния, разрешает
  `max_iterations` (аргумент вызова → `.env` → 6).
- `redi_decompose` — декомпозиция + обогащение вопроса (см. §4).
- `init_blackboard` — из подзапросов создаёт исходные `Task`, инициализирует скелет вики
  (`index.md`, `log.md`).

**Фан-аут оркестратора.** Условное ребро `route_from_orchestrator` возвращает **список
`Send()`** — по одному на целевой узел — для параллельного запуска агентов, либо строку
для прямого перехода к критику. Важное решение: `Send` формируется **на узел, а не на
директиву** — каждый узел агента получает все свои директивы разом, чтобы не дублировать
дорогую работу (`orchestrator.py:428-439`).

**Фан-ин.** Все три агента-исполнителя и медиатор ведут к единственному узлу `wiki_curator`
— это точка синхронизации раунда.

**Два выхода из цикла.** `wiki_curator` может сам решить завершить (достигнут лимит итераций
→ `finish_ready`) или направить к критику; критик принимает окончательное STOP/CONTINUE.
Оба пути завершения ведут в `final_synthesis`, который единственный имеет ребро в `END`.

Компиляция графа выполняется на каждый `run()`; активная модель прокидывается через
`set_active_model()` перед сборкой.

## 3. Трёхуровневая память BlackBoard

`state.py::BlackBoard` — единственный источник истины, разделяемый всеми узлами (`TypedDict`,
`total=False`). Агенты **не общаются напрямую** — только через операции чтения/записи по
доске. Это одновременно реализует и разделяемую память, и косвенную коммуникацию, и позволяет
пути решения эволюционировать по мере поступления новых данных.

Три уровня знаний (формула из статьи: `B = (R, W, O)`):

| Уровень | Поле | Семантика | Reducer |
|---|---|---|---|
| **R** — сырьё | `raw_data` | Append-only журнал всех выходов агентов (`RawEntry`) | `operator.add` |
| **W** — вики | `wiki` | Структурированные страницы знаний, upsert по `page_id` | `_merge_wiki` (right wins) |
| **O** — факты | `output` | Подтверждённые факты, upsert по `fact_id` | `_merge_output` (побеждает бо́льшая уверенность) |

**Решение о reducer'ах.** LangGraph при параллельном фан-ауте сливает частичные обновления
состояния через `Annotated`-редьюсеры. Поэтому:
- `raw_data` только добавляется (никогда не перезаписывается) — журнал неизменяем;
- `output` при конфликте `fact_id` оставляет запись с **более высокой** уверенностью
  (`_merge_output`, `state.py:150-164`) — реализация правила «конфликт решается уверенностью»;
- `wiki` — простой dict-merge, где правый операнд побеждает.

**Ключевые типы данных.**
- `SubQuery` — подзапрос ReDI: `intent_aspect`, `search_modality` (`web|normative|code|any`),
  `enriched_variants`, `keywords`, `domain_hints`.
- `Task` — единица очереди: `assigned_agent`, `status` (`pending|in_progress|done|failed`),
  `proposer`, `directive`. Upsert по `task_id`.
- `RawEntry` — выход агента: `type`, `content`, `confidence`, `tool_trace`, `citations`,
  `curated`. Создаётся через фабрику `board_message()`.
- `WikiPage` — `content` (markdown с `[[cross-refs]]` и маркерами `> CONFLICT:`),
  `incoming_cross_refs`, `relevance_score`.
- `ConfirmedFact` — `claim`, `source_agents`, `confidence`, `limitations`, `sub_query_id`.

**Служебные поля управления циклом:** `iteration`, `max_iterations`, `stop_flag`, `critique`,
`next_action`, `stagnation_count`, `progress_delta`, а также `ablation` (см. §13) и
`agent_trace`/`errors` для мониторинга.

## 4. ReDI — декомпозиция, обогащение, слияние

**ReDI** (*Retrieval-oriented Decomposition Index*) — три стадии в пакете `redi/`.

### Стадия A — Декомпозиция (`decomposer.py`)

`ReDIDecomposer` разбивает исходный вопрос на **3–5 независимых подзапросов** (LLM,
`temperature=0.0`), каждый покрывает ровно один аспект и получает:
- `search_modality` — подсказку модальности `web | normative | code | any`;
- `intent_aspect` — короткую метку измерения.

Валидация выхода — через Pydantic-модели `_SubQuerySpec`/`_SubQuerySet` с регексом на
модальность. Проектное решение системного промпта: вопросы вида «какие улицы/объекты/зоны
существуют в названной географической области; посчитать / измерить / классифицировать
географические признаки» жёстко относятся к `code`, потому что отвечаются через
OpenStreetMap (osmnx), а не веб-поиском.

### Стадия B — Обогащение (`enricher.py`)

`ReDIEnricher` (LLM, `temperature=0.2`) для каждого подзапроса генерирует **до внешних
вызовов**:
1. 3 альтернативные формулировки (`enriched_variants`);
2. 5–10 ключевых терминов (`keywords`) — используются позже в скоринге Fusion;
3. `domain_hints` — доменные идентификаторы (`СНиП`, `ГОСТ`, `SanPiN`) для нормативных
   подзапросов или имена библиотек для code-подзапросов; пустой список для web.

Смысл — повысить полноту (recall) последующего извлечения ещё до сетевых обращений.

### Стадия C — Слияние (`fusion.py`)

`ReDIFusion` вызывается **внутри** `wiki_curator` на каждом раунде. Для каждого подзапроса:
- **дедупликация** записей `raw_data` по токенной Jaccard-близости (`≥ 0.7`; при дубле
  остаётся запись с большей уверенностью);
- **скоринг** каждой находки = `keyword_overlap × confidence`;
- **аддитивная оценка** top-N (`N=5`) и сводка → пишется в `wiki["redi_fusion"]`.

**Важно (из статьи и промпта оркестратора):** модальность — только **маршрутизирующий
контекст**, а не жёсткое ограничение. Финальный выбор исполнителя остаётся за оркестратором.

### Гарантия количественной опоры

`blackboard.py::_ensure_code_spatial_sub_query` добавляет подзапрос `sq_code_support`, если
среди подзапросов нет ни одного с модальностью `code`. Если в вопросе распознано конкретное
место (эвристика `_extract_named_place` — паттерн «`<место>. <вопрос>`» из бенчмарка), в
директиве фиксируется этот scope; иначе агенту явно запрещено выдумывать место и предписано
вернуть `LIMITATIONS: location not specified`. Так пайплайн всегда получает хотя бы одну
попытку количественно-пространственного анализа.

## 5. Оркестрация и маршрутизация по способностям

`nodes/orchestrator.py::orchestrator_node` — «мозг» цикла. Читает состояние доски и решает,
каких агентов активировать.

### Маршрутизация по карточкам способностей

Вместо фиксированной таблицы «модальность → агент» оркестратор выбирает исполнителя
**LLM-рассуждением над структурированными карточками способностей** (`capabilities.py`).
Каждая `AgentCapability` содержит `description`, `handles`, `cannot_do` — то есть агент
описывает и что умеет, и **чего не умеет**. Именно узкий, сфокусированный набор способностей
у каждого исполнителя и делает возможной осмысленную маршрутизацию.

`_llm_choose_agent` (`temperature=0.0`) получает текст подзапроса, подсказку модальности,
брифинг текущей вики (`wiki_briefing`) и список карточек **за вычетом уже испробованных
агентов**, затем возвращает выбор в JSON. Подсказка модальности — контекст, не ограничение;
но для `search_modality == "code"` есть быстрый детерминированный путь в обход LLM.

### Правила и защитные механизмы

`orchestrator_node` реализует набор жёстких правил:

1. **Анти-дубль.** Пара `(agent, sub_query_id)` со статусом `done` никогда не переназначается
   (`_get_done_pairs`).
2. **Переназначение при провале** (`_detect_and_reassign_failed`). Провал = уверенность
   `< 0.4` **или** контент начинается с «Agent stopped due to…». Провальный подзапрос
   отдаётся агенту, который его **ещё не пробовал**; если все специализированные агенты уже
   пробовали — переназначения нет. Успешный результат по подзапросу отменяет переназначение.
3. **Анти-стагнация.** При `stagnation_count >= 2` — принудительный переход к критику.
4. **Лимит 3 диспатча за раунд** (`_MAX_DISPATCHES_PER_ROUND`) — против взрывного роста
   контекста.
5. **Диспатч медиатора** — только когда получены результаты ≥ 2 других агентов и синтеза
   ещё не было (и только если включён уровень `blackboard`).
6. **Приоритет `sq_code_support`** — количественная опора сортируется вперёд очереди.

Продиспатченные задачи помечаются `in_progress`, формируется список `OrchestratorDirective`
с обогащённой директивой (подзапрос + до 2 `enriched_variants`; `domain_hints` добавляются
только для `NormativeAgent`).

### Реестр способностей (`capabilities.py`)

- `AGENT_CAPABILITIES` — три карточки: `WebSearchAgent`, `NormativeAgent`, `CodeSpatialAgent`.
- `MODALITY_TO_AGENT` — детерминированный фолбэк; заметно, что `ANY → CodeSpatialAgent`
  (неоднозначные пространственные/open-data задачи требуют кода в первую очередь).
- `AGENT_TO_NODE` — соответствие имён агентов узлам графа.

## 6. Специализированные агенты-исполнители

Все три исполнителя — **ReAct-агенты** на LangChain `AgentExecutor` с
`return_intermediate_steps=True`. Каждый получает **небольшой сфокусированный** набор
инструментов (не общий пул) — именно это и делает возможной маршрутизацию по способностям.
Каждый пишет `RawEntry` в `raw_data` через `board_message()`, парся собственный контракт
вывода (`ANSWER/CONFIDENCE/SOURCES` и т.п.). Все три поддерживают **toolless-режим**
(`toolless.py::run_toolless`) для ablation — одноразовый вызов LLM без инструментов.

Общий паттерн узла: отфильтровать директивы для себя (`target_agent`), для каждой запустить
исполнителя, распарсить, при исключении записать низкоуверенную failure-запись (никогда не
роняя граф).

### 6.1 WebSearchAgent (`agents/web_search.py`)

- **Роль:** факты, текущий статус, описания проектов, новости из открытого веба; извлечение
  URL-источников и коротких цитат.
- **Инструменты:** `web_search_tool`, `research_url_tool`.
- **Тип:** `create_tool_calling_agent`, `temperature=0.1`, `max_iterations=6`.
- **Решения промпта:** ≤ 3 поисковых запроса; дип-рид только top-1–3 URL (не читать всё);
  контракт `ANSWER / CONFIDENCE / SOURCES`.
- **Защитная обёртка** `_make_guarded_research_tool`: дедуплицирует URL и жёстко ограничивает
  дип-рид **3 уникальными URL** на подзапрос.
- **Скоринг уверенности:** `0.8+` — несколько подтверждающих источников; `0.6–0.8` — один
  надёжный; `<0.6` — косвенно. Если агент не указал уверенность — она принудительно
  занижается до `≤ 0.4` с пометкой в limitations.
- **Фолбэк:** если `ANSWER` пуст — берётся последняя успешная выжимка `research_url_tool`;
  если и её нет — извлекаются URL прямо из текста.

### 6.2 NormativeAgent (`agents/normative.py`)

- **Роль:** законы, регламенты, стандарты, обязательные требования; имена документов,
  разделы, пункты и точные цитаты.
- **Инструменты:** `normative_vector_search_tool` (локальный RAG), `normative_web_search_tool`,
  `fetch_url_tool`.
- **Тип:** классический `create_react_agent` (текстовый ReAct-формат), `temperature=0.0`,
  `max_iterations=8`, с `handle_parsing_errors` (мягкое напоминание о формате).
- **Стратегия:** сначала локальная векторная БД → если найдено < 2 релевантных чанков →
  целевой веб-поиск → при возможности верификация цитат через `fetch_url_tool`. Всегда:
  имя документа, номер раздела, точный текст требования.
- **Скоринг:** `0.9` — найдено в локальной нормативной БД с точной цитатой; `0.7` — через
  веб с именем документа и разделом; `0.5` — косвенная ссылка.
- **Более строгий порог продвижения** (`0.7` против `0.65` у остальных, см. §8) отражает
  повышенные требования к нормативным утверждениям.

### 6.3 CodeSpatialAgent (`agents/code_spatial.py`)

- **Роль:** количественные и пространственные подзапросы; данные из OpenStreetMap (osmnx),
  геометрия, маршруты, расстояния, буферы, доступность, подсчёты, геокодирование.
- **Инструменты:** `run_validated_python` (в защитной обёртке), `inspect_api_tool`,
  `find_capability_tool`, `check_available_data_tool`, `list_available_libraries_tool`.
- **Тип:** `create_tool_calling_agent`, `temperature=0.0`, `max_iterations=8`.
- **Жёсткий пайплайн рассуждения:**
  `HYPOTHESIS → PLAN → CODE → EXECUTE → INTERPRET`, финальный контракт —
  `HYPOTHESIS / PLAN / RESULT / NUMERIC SELF-CHECK / CONFIDENCE / LIMITATIONS`.
  Делегирование детерминированных операций исполняемому коду (вместо текстовой аппроксимации)
  снижает пространственные галлюцинации и даёт трассируемость числовых свидетельств.
- **Capability cards (CARD).** Перед кодом `PLAN` обязан сослаться хотя бы на одну
  проверенную карточку (`retrieve_capabilities`, k=4, инъекция в системный промпт). Если
  карточка не подходит — вызвать `find_capability_tool`; при сомнении в функции —
  `inspect_api_tool("module.function")`.
- **Location guardrail.** Если место названо — использовать только его; если не названо —
  запрещено подставлять плейсхолдеры (`region X`, `<place>`), нужно вывести реальное место
  или завершить с `LIMITATIONS`. `NUMERIC SELF-CHECK` обязателен.
- **Loop-guard** `_make_guarded_python_tool`: отвергает повторный идентичный код (по SHA-256
  нормализованного сниппета) и после **3** подряд неуспешных/дублирующих запусков предписывает
  прекратить исполнение и выдать интерпретацию-или-фолбэк.
- **Пост-обработка `_parse_output`:** если в `RESULT` есть числа, но нет `NUMERIC SELF-CHECK`
  — уверенность занижается до `≤ 0.3` с пометкой «unverified scope»; то же при
  плейсхолдер-подобном scope. Если текст не выдал числовой `RESULT`, но был успешный запуск
  кода — контент берётся из последнего успешного вывода с уверенностью `0.3`.
- **Философия «augment, not gate»:** провалы исполнения не повод отказываться от ответа —
  результат кода это низкоуверенное **дополнение** к финальному ответу, а не условие его
  выдачи.

---

## 7. MediatorAgent — кросс-источниковый синтез

`nodes/mediator.py::mediator_node` — не исполнитель, а синтезатор. Читает **всю вики** и
подтверждённые факты, затем:

1. **AGREEMENTS** — где несколько агентов подтверждают одно и то же;
2. **CONTRADICTIONS** — где агенты расходятся (с разницей уверенностей);
3. **SYNTHESIS** — нарратив, который **лидирует единым прямым ответом** на вопрос, затем
   подкрепляет его подтверждёнными фактами;
4. **UPDATE OUTPUT** — новые `ConfirmedFact` с мультиисточниковой атрибуцией.

**Правило продвижения медиатора:** факт попадает в `output`, только если согласны ≥ 2
независимых источника **или** уверенность `≥ 0.75`. Даже при зафиксированных противоречиях
`synthesis_narrative` обязан коммитить единую наиболее обоснованную позицию (взвешенную по
уверенности и согласию источников) — противоречия записываются отдельно, но не «размывают»
ответ.

Результат: страница `wiki["synthesis"]` (с секцией `## Unresolved Contradictions`) и запись
`mediator_synthesis` в `raw_data`. Медиатор всегда ведёт к `wiki_curator`.

---

## 8. WikiCurator и подсистема вики

`nodes/curator.py::wiki_curator_node` — центральный fan-in узел после всех агентов. Именно
здесь `raw_data` превращается в структурированную вики и подтверждённые факты. Инкрементирует
`iteration`.

### Обязанности

1. **Обработка `raw_data` → `WikiPage`.** Отбираются некурируемые, непровальные, несистемные
   записи текущего раунда (`_get_processable`; пропускаются типы `init`,
   `orchestrator_directive`, `critique`, `curator_summary` и failure-префиксы). Для каждой —
   `WikiPageBuilder.build` (новая страница) или `.update_page` (аппенд к существующей).
   `page_id = "{agent_slug}_{sub_query_id}"`.
2. **ReDI Fusion** — если уровень `redi` включён (см. §4C).
3. **Обслуживание вики** (`wiki/maintenance.py`, порядок важен):
   - `update_incoming_cross_refs` — пересборка входящих ссылок по маркерам `[[page_id]]`;
   - `compute_relevance_scores` —
     `relevance = (incoming_refs + 1) × confidence × sq_match_bonus`,
     где `sq_match_bonus = 1.5`, если теги страницы пересекаются с `intent_aspect`
     какого-либо подзапроса (`+1`, чтобы новые страницы не обнулялись сразу);
   - `prune_wiki` — удаляет страницу, только если **одновременно**: не защищена,
     `confidence < 0.35`, нет входящих ссылок, теги не пересекают `intent_aspect`, и
     возраст `≥ 2` итерации; висячие `[[…]]`-ссылки на удалённое чистятся;
   - `merge_overlapping_pages` — сливает пары страниц с Jaccard `≥ 0.75`, обновляя
     перекрёстные ссылки `[[id_b]] → [[id_a]]`.
   - Защищённые страницы (`index.md`, `log.md`, `redi_fusion`, `synthesis`, `task_context`)
     никогда не прунятся/сливаются.
4. **Продвижение фактов в `output`** (`_should_promote`): непровальный, `len(content) ≥ 50`,
   и порог по типу:
   - `normative_findings`: `confidence ≥ 0.7`;
   - `web_findings | code_result | mediator_synthesis`: `confidence ≥ 0.65`.
5. **`index.md` и `log.md`** пересобираются каждый раунд (`wiki/index.py`, `wiki/log.py`).
   `index.md` — markdown-таблица всех страниц (page_id/title/agent/confidence/relevance);
   `log.md` — журнал действий (`page_created`, `page_updated`, `fact_promoted`,
   `conflict_flagged`, `pages_merged`).
6. **Детекция стагнации:** `progress_delta = len(processable)`; если `0` —
   `stagnation_count += 1`, иначе сброс в `0`.

### Построение страниц (`wiki/page.py`)

- **Инъекция перекрёстных ссылок** `_inject_cross_refs`: упоминание заголовка другой
  страницы в контенте заменяется на `title [[page_id]]` (один раз, без дублирования).
- **Детекция конфликтов** `_detect_conflict`: если новый и существующий контент нетривиальны
  (`≥ 50` символов) и их Jaccard `< 0.25` — вставляется маркер `> CONFLICT:`. Это простая
  эвристика «низкое пересечение по одному аспекту → возможное противоречие».
- **Обновление страницы** аппендит новый контент с разделителем и датой итерации,
  дедуплицирует цитаты по URL, берёт `max` уверенности.

### Маршрутизация после куратора (`route_from_curator`)

- `iteration >= max_iterations` → `finish_ready` (прямо в синтез, минуя критика);
- если есть подтверждённые факты (`output`) → `critic`;
- иначе → `continue` (обратно к оркестратору).

## 9. CriticAgent — управление циклом

`nodes/critic.py::critic_node` — оценщик, принимающий решение STOP / CONTINUE и при
необходимости инжектирующий новые задачи в очередь.

### Иерархия решений (сверху вниз)

1. **Force-STOP без LLM:** `iteration >= max_iterations` **или** `stagnation_count >= 2`.
   `_build_force_stop_critique` вычисляет покрытие и среднюю уверенность, ставит
   `force_stop=True`.
2. **Гейт количественной опоры:** если существует `sq_code_support`, но `CodeSpatialAgent`
   по нему ещё не отработал — принудительный `CONTINUE` (нельзя останавливаться до
   количественной проверки).
3. **Быстрый STOP:** если все подзапросы покрыты (`covered`) и есть факты — STOP без LLM.
4. **LLM-критика** (`_run_thinking_critique` через `call_with_thinking`) — оценивает
   достаточность свидетельств. Возвращает `action`, `overall_confidence`, `reasoning`,
   `new_tasks`, `contradictions`. **Покрытие всегда пересчитывается детерминированно**
   (`coverage_from_sub_queries`) и перекрывает значения от LLM как более надёжное. При ошибке
   парсинга — консервативный `CONTINUE`.

### Критерии STOP (для LLM)

Любой из: все подзапросы имеют подтверждённый факт с уверенностью `≥ 0.7`; либо факты в
совокупности дают полный, хорошо обоснованный ответ.

### Инжекция задач

При `CONTINUE` каждый элемент `new_tasks` (с указанием `sub_query_id`, `assigned_agent`,
`directive`, `priority`) превращается в новую `Task` со статусом `pending` и `proposer =
CriticAgent` — так критик «дозаказывает» исследование конкретных пробелов покрытия.

`route_from_critic`: `stop_flag` или `action == STOP`/`force_stop` → `finish`, иначе
`continue`.

Покрытие (`coverage_from_sub_queries`): для каждого подзапроса — `covered` (есть факт с
уверенностью `≥ 0.7`), `partial` (факт есть, но слабее), `pending` (фактов нет).

## 10. Финальный синтез (fail-open)

`nodes/synthesis.py::final_synthesis_node` вызывается после выхода из цикла. Собирает
подтверждённые факты (отфильтровав failure-претензии), нарратив медиатора
(`wiki["synthesis"]`) и нерешённые противоречия критика в финальный ответ.

### Трёхпроходная цепочка `draft → critique → refine`

`_run_synthesis_chain` (`temperature=0.1`) выполняет три вызова LLM с разными системными
промптами:
1. **DRAFT** (`_SYNTHESIS_SYSTEM`) — черновик по фактам;
2. **CRITIQUE** (`_CRITIQUE_SYSTEM`) — строгая критика: читается ли это как настоящее,
   закоммиченное экспертное рассуждение, а не как хедж/чеклист/пересказ вопроса;
3. **REFINE** (`_REFINE_SYSTEM`) — доработка как **Pareto-улучшение** (усилить
   раскритикованное, не ослабляя уже сильное).

### Формат: экспертное memo из 7 секций

`Answer` · `How I'm reading the question` · `What it hinges on` · `Options I weighed` ·
`The case for it` · `What's still uncertain` · `Where this reasoning could be wrong`.

**Проектные решения промптов:**
- Промпты **домен-нейтральны** — работают для вопроса из любой области.
- Обязательный **fail-open**: лидировать прямым конкретным ответом; даже при частичных или
  конфликтующих свидетельствах выбрать единственный наиболее обоснованный (взвешенный по
  уверенности и согласию источников) и заявить его как вывод; не отказываться и не хеджировать
  сам вывод.
- Последняя секция — **рассуждение о самом рассуждении** (rejected framings, калибрация
  уверенности для 2–3 несущих утверждений, смещение из-за способа сбора свидетельств,
  слабейшее звено, остаточные риски), а не второй раунд доменного хеджирования.

### Фолбэк

При исключении LLM — `_fallback_answer` детерминированно форматирует факты в то же
7-секционное memo (лидируя фактом с максимальной уверенностью), сохраняя fail-open-контракт.

Опционально вики персистится на диск, если задан `WIKI_PERSIST_DIR`.

## 11. Инструменты (tools)

Инструменты реализованы как LangChain-обёртки и прикреплены к соответствующим ReAct-агентам.
Оркестратор, куратор, медиатор и критик **не вызывают внешних инструментов** — они работают
напрямую по доске. Два сквозных принципа проектирования инструментов:

- **У каждого внешнего канала есть фолбэк**: `Tavily → DuckDuckGo`, `локальный RAG → веб`,
  `E2B → subprocess`. При недоступности источника инструмент возвращает явный маркер для
  снижения уверенности, а не падает.
- **Исполняемый код проходит проверки** (safety, существование API, статический анализ) до
  запуска, а веб-страницы дистиллируются в структурированные evidence-заметки, а не сырой
  текст. Это даёт трассируемость свидетельств и устойчивость к галлюцинациям.

### 11.1 Веб (`tools/web_search.py`)

| Инструмент | Назначение | Реализация |
|---|---|---|
| `web_search_tool` | Поиск по запросу | Tavily (`search_depth="advanced"`) → фолбэк DuckDuckGo (`ddgs`/`duckduckgo_search`); при заблокированных/пустых результатах — авто-перефраз запроса |
| `research_url_tool` | Дип-рид 1–3 ссылок | Извлечение основного текста (`trafilatura` → `readability` → BeautifulSoup) + **LLM-дистилляция** в evidence-заметки (claims, numbers, quotes, `source_url`, limitations); LRU-кэш; при провале — экстрактивный фолбэк |
| `normative_web_search_tool` | Веб для нормативки | Обёртка над `web_search_tool` с доменными хинтами (RU/EN автоопределение по кириллице) |
| `fetch_url_tool` | Верификация цитат | Загрузка страницы, извлечение первых 3000 символов |

Детектор «плохих результатов» `_looks_like_bad_results` ловит маркеры блокировок (`403`,
`request_forbidden`, `unsupported_country_region_territory`) и запускает перезапрос.

### 11.2 Нормативный RAG (`tools/vector_store.py`)

`normative_vector_search_tool` — семантический поиск по локальному корпусу `data/normative/`
(`.pdf`, `.txt`, ленивая инъекция при первом вызове):
- Chroma + мультиязычные эмбеддинги `paraphrase-multilingual-MiniLM-L12-v2`;
- чанки `800/100`, `top-k = 4`, источник/страница в метаданных;
- при пустом корпусе — эфемерный store, возвращающий пусто; при отсутствии зависимостей —
  явный маркер «continue with web search».

### 11.3 Исполнение кода (`tools/code_exec.py`)

`run_validated_python` (предпочтительный для CodeSpatialAgent) прогоняет **три проверки до
запуска** (`_pre_execution_check`):
1. `_ast_safety_check` — запрет `subprocess/eval/exec/__import__/compile/pty/pexpect` и
   `os.system/popen/execv/fork/kill/spawn*`;
2. `_api_existence_check` — ловит **галлюцинированные** `module.attr` через реальный
   `importlib` + `getattr`, предлагает похожие имена (`difflib`);
3. `_ruff_pyflakes_check` — статанализ `ruff --select F` (пропускается, если ruff не
   установлен).

**Бэкенды исполнения:** E2B-песочница, если задан `E2B_API_KEY` (изолированная, сетевая),
иначе — subprocess (сеть разрешена, таймаут 120 с). Разрешены `osmnx, geopandas, shapely,
geopy, requests, httpx, pandas, numpy, networkx` и др. Переменная `DATA_DIR` всегда доступна
в коде. Утилиты: срезание markdown-ограждений, авто-`print` последнего выражения.

Вспомогательные инструменты: `inspect_api_tool` (сигнатура+докстринг объекта по dotted-имени),
`check_available_data_tool` (инвентаризация `DATA_DIR`), `list_available_libraries_tool`
(список установленных библиотек по категориям).

### 11.4 Реестр способностей (`tools/tool_registry.py`)

`retrieve_capabilities` возвращает top-k **проверенных карточек** (`data/tool_kb/*.json`):
семантический поиск (Chroma, те же мультиязычные эмбеддинги) с фолбэком на keyword-overlap.
Карточка: `id`, `name`, `when_to_use`, `libs`, `verified_snippet`, `io_contract`, `pitfalls`.
`format_capability_cards` экранирует фигурные скобки, чтобы примеры кода не стали переменными
prompt-шаблона. `find_capability_tool` — инструмент для агента.

## 12. Инфраструктура: LLM, конфигурация, учёт токенов

### LLM-фабрика (`llm.py`)

Всё инстанцирование моделей идёт через `get_chat_model()` — `ChatOpenAI`, направленный на
OpenAI-compatible backend (`base_url` из настроек), с общим httpx-клиентом (пул соединений),
`disable_streaming=True`, кэшированием по `(model_id, temperature, max_tokens)`. Активная
модель задаётся `set_active_model()` перед сборкой графа (сбрасывает кэш). `call_with_thinking`
— единый вызов для медиатора и критика (возвращает `(thinking, answer)`; thinking-канал
сейчас пуст, интерфейс сохранён).

### Конфигурация (`config.py`)

`Settings` (frozen dataclass, `@lru_cache`) читается из `.env`:
`FP2MP_CHAT_URL`, `FP2MP_API_KEY` (обязателен — иначе `ConfigurationError`), `TAVILY_API_KEY`,
`E2B_API_KEY`, `MAX_ITERATIONS` (6), `SYNTHESIS_REFINE`, `NORMATIVE_DB_PATH`,
`WIKI_PERSIST_DIR`, `LOG_LEVEL`.

### Учёт токенов (`usage.py`)

`TokenUsageAccumulator` (LangChain callback) — авторитетный итог по токенам за прогон:
- если бэкенд вернул реальные числа (`usage_metadata`/`token_usage`) → `source="real"`;
- иначе — tiktoken-оценка (`cl100k_base`) по промптам и ответам → `source="estimate"`.

Оценка считается **отдельно** от per-message оценок в `log`, чтобы суммирование лога не
задваивало итог. В `graph.py::_build_log` каждое `AIMessage` несёт свою per-message
tiktoken-оценку (`input_tokens` — размер предшествующего промпта, `output_tokens` — размер
собственного контента) исключительно для отображения.

## 13. Ablation — переключаемые компоненты

`ablation.py::AblationConfig` (frozen dataclass) — рантайм-переключатели для экспериментов по
отключению компонентов; все поля по умолчанию `True` (продакшн-пайплайн). Конфиг передаётся
как **параметр** (`create_initial_state(..., ablation=...)`), а не через изменение `state.py`,
и кладётся в `state["ablation"]`; узлы читают его через `get_ablation(state)`.

Четыре флага:

| Флаг | Что отключает |
|---|---|
| `redi` | ReDI-декомпозицию/обогащение (один подзапрос = весь вопрос) и ReDI Fusion в кураторе |
| `blackboard` | Построение вики и продвижение фактов; куратор лишь считает записи, `output` формируется из `raw_data` напрямую, синтез читает `raw_data` |
| `critic` | LLM-критику → детерминированный force-STOP (по лимиту итераций / стагнации / отсутствию pending-задач) |
| `tools` | Инструменты у всех трёх исполнителей → toolless-режим (`run_toolless`) |

Полная карта из **12 отключаемых компонентов** (топологические / смешанные / поведенческие),
их зависимостей и каскадных рисков — в `docs/ablation_components.md`. Ключевые связанные пары:
«Wiki OFF ⟺ Mediator в fallback-режиме» и «Critic OFF ⟺ `max_iterations=1`».

## 14. Публичный API и формат результата

### Высокоуровневый вызов

```python
from fp2mp_core.graph import run

result = run(
    input="Какие улицы Петроградского района можно сделать пешеходными?",
    model="gpt-4o-mini",
    max_iterations=3,          # опционально
    ablation=None,             # опционально: AblationConfig(...)
)
```

`run()` возвращает `BaseState` — формат, совместимый с `fp2mp-baselines`/`fp2mp-eval`:

| Поле | Тип | Описание |
|---|---|---|
| `input` | `str` | Исходный вопрос |
| `output` | `str` | Финальный синтезированный ответ (memo из 7 секций) |
| `log` | `list[BaseMessage]` | Трасса в формате LangChain messages; каждое `AIMessage` несёт per-message tiktoken-оценку |
| `usage` | `dict` | Авторитетный итог: `{input_tokens, output_tokens, total_tokens, source}` (`real`/`estimate`) |

### Низкоуровневый доступ к полному BlackBoard

```python
from fp2mp_core.graph import build_graph
from fp2mp_core.state import create_initial_state

graph = build_graph()
state = create_initial_state(question, max_iterations=8)
result = graph.invoke(state)   # полный BlackBoard со всеми уровнями памяти
```

Модель задаётся через `.env` и передаётся в `run(..., model=...)`, чтобы один и тот же backend
переиспользовался в `fp2mp-baselines`/`fp2mp-eval` с разными моделями и числом итераций.
Платные прогоны (`run()` и судья) пользователь запускает вручную.
